# ADR-0008: Anything-mode inline libraries — markers stored, vendored bytes injected at render time

## Status

Accepted — 2026-07-09

## Context

Anything mode's sandbox contract bans all network access, so agent pages could only use vanilla JS. That rules out an entire class of asks (force-directed graphs, real scales/axes, geo projections) or tempts the agent to re-implement library internals badly inside its ~200KB budget. We want allowlisted libraries (starting with d3) available inside the sandbox **without weakening any safety invariant**:

- the iframe stays `sandbox="allow-scripts"` only, CSP unchanged — no network, ever;
- library bytes are **pinned and vendored** (npm-sourced, committed, versioned), never agent-supplied and never fetched;
- everything agent-authored still runs the full validation ladder.

The mechanism: the agent writes an HTML comment marker — `<!-- @lib:d3 -->` — and the platform splices in the vendored source as an inline `<script>`. The key design decision is **where** the splice happens: server-side at accept time (store the expanded document), or at render/execute time (store the marker form, expand where the document actually runs).

## Decision

**Render/execute time.** The slot stores the marker form; `expandAnythingLibs` (shared) is called at the two execution points — the client renderer just before `iframe srcDoc`, and the server's jsdom runtime check. Reasons, in the order they decided it:

1. **Revision history size.** d3 alone is ~273KB. Accept-time injection would put those bytes into _every_ revision of the slot's history, every AG-UI patch event, and every session-events proposal payload — a 100-line agent document becomes a ~280KB wire object on each edit. Marker-form storage keeps revisions at agent-content size.
2. **Client-sync round-trips.** The client syncs the live document back through `syncClientDiagramSource`, which re-runs the static ladder. If the stored form were expanded, the synced document would carry the lib bytes back into validation: the policy lint would false-positive on URLs inside library comments (d3's first line is `// https://d3js.org …`), the size cap would trip, and a re-accept would risk double-injection. With marker form, what round-trips is exactly what the agent authored — it revalidates cleanly, and expansion (which replaces the marker) is idempotent by construction: an expanded document has no marker left to expand.
3. **Agent edits.** `apply_anything_edit` does search/replace against the current document, which sits in the agent's context. Minified library bytes in that context would wreck both token cost and edit-match reliability.
4. **MCP resource exposure.** External agents reading the slot over MCP get the compact marker form — they author, they don't render. Anything that _does_ need to render (a future MCP App preview) calls the same shared `expandAnythingLibs`.

### Mechanics

- **Registry metadata** (`packages/shared/src/anythingLibs.ts`, barrel-exported): lib ids, pinned versions, globals, prompt one-liners; marker regex; `lintAnythingLibMarkers` (unknown id → `unknown_lib` rejection naming the allowlist); `describeAnythingLibsForPrompt` so the system prompt is generated from the registry and cannot drift.
- **Vendored bytes** (`packages/shared/src/vendor/anythingLibSources.ts`, generated — do not hand-edit): regenerated by `npm run vendor:anything-libs -w packages/shared` from exact-pinned devDependencies. The generator asserts the source contains no `</script`, `<!--`, or `<script` sequences (it must survive inline `<script>` embedding verbatim).
- **Expansion** (`packages/shared/src/anythingLibVendor.ts`): replaces each allowlisted marker with `<script data-archislop-lib="…" data-lib-version="…">…</script>`; duplicate markers inject once; unknown markers pass through as inert comments (upstream validation already rejected them for agent content). Deliberately **not** in the index barrel — it's behind the `@archislop/shared/anythingLibVendor.js` subpath export so the web main bundle doesn't carry the bytes; `AnythingRenderer` dynamic-imports it only when a document has markers (separate Vite chunk, loaded once).
- **Ladder placement** (`anythingHtmlTool.js`): every static gate (shape/size, policy lint, quality lint, marker lint) runs on the **marker form** — so the ~200KB `ANYTHING_HTML_MAX_LENGTH` budget applies to agent-authored content only, and the policy lint never sees vendored source. Only the jsdom **runtime check executes the expanded document**, i.e. the page is executed with the same bytes the client will inject.

## Consequences

Positive:

- Zero change to the security boundary: same sandbox, same CSP, no network; injected code is repo-reviewed, pinned, npm-provenance bytes.
- Revisions, SSE payloads, MCP resources, and agent edit contexts stay agent-content-sized.
- Registry-driven prompts + `unknown_lib` errors give agents a self-correcting allowlist.

Trade-offs accepted:

- A document is now self-contained _modulo the app's registry_: renderers outside archislop must call `expandAnythingLibs` (or accept the marker as a dead comment). This is the price of not persisting 273KB per revision.
- Old revisions re-render with whatever version the registry pins **now**, not the version at authoring time. Acceptable for a canvas tool; the injected `data-lib-version` attribute makes it observable.
- The web app pays a one-time lazy ~280KB chunk (~90KB gzipped) the first time a lib-using document renders.
- Each new library grows the repo and that chunk, so the allowlist is meant to stay short; additions need a registry entry, a pinned devDep, regeneration, and bench/test coverage.

Explicitly out of scope (ideas, not scheduled): a "deep build" tier where external agents compose larger apps over MCP, and an LLM-driven bench extension (`benchAnything --with-llm`) — both flagged in the planning brief.

## Alternatives considered

- **Server-side injection at accept time.** Rejected for the four reasons above: revision/wire bloat, client-sync round-trips (policy-lint false positives on library-comment URLs, size-cap trips, double-injection risk), minified bytes in `apply_anything_edit` contexts, and heavyweight MCP resources.
- **Ambient injection (no marker).** Always inject d3 so pages "just work". Rejected: every page pays the bytes and jsdom execution cost, and there is no explicit, lintable opt-in for agents to reason about. The bench keeps a `runtime-lib-without-marker` case to ensure ambient injection never creeps in.
- **Runtime read from `node_modules` / CDN allowlist in CSP.** Reading dist files at runtime couples prod images to devDependencies and gives the web no story; loosening CSP for a CDN violates the no-network invariant outright. Vendored, committed, generator-verified bytes are the only variant where review, pinning, and offline behavior all hold.

## Where this lives in code

- Registry + marker lint: `packages/shared/src/anythingLibs.ts` (barrel-exported)
- Expansion + vendored bytes: `packages/shared/src/anythingLibVendor.ts` (subpath export `@archislop/shared/anythingLibVendor.js`), `packages/shared/src/vendor/anythingLibSources.ts` (generated), `packages/shared/scripts/vendorAnythingLibs.mjs`
- Ladder: `apps/server/src/tools/anythingHtmlTool.js` (marker lint + expanded runtime check)
- Client: `apps/web/src/components/AnythingRenderer.jsx` (lazy vendor chunk, expansion before `wrapAnythingSrcDoc`)
- Prompts: `apps/server/src/prompts/anythingSystemPrompt.js`, `anythingSyntaxGuard.js` (generated from the registry)
- Bench: `apps/server/scripts/benchAnythingCorpus.js` (`valid-lib-d3`, `policy-unknown-lib`, `runtime-lib-without-marker`)
