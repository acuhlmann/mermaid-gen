One system, three questions

ArchiSlop uses several generative-UI technologies at once — AG-UI, A2UI, five content-slot languages, MCP Apps. They are not competitors. Each answers a different question, and conflating the questions is the main way to get confused.

Companion to architecture-generative-ui.md — this page is the intuition; that page is the contract. Linked docs open on GitHub (rendered markdown); this page is self-contained HTML.

The map. A transport carries payloads; a payload language says what was generated; a placement says where a human sees it. Any payload can, in principle, ride any wire to any surface — the combinations below are the ones ArchiSlop actually ships.

Axis 1 · Transport

AG-UI is the wire, not the widget

AG-UI is an event vocabulary between an agent backend and a frontend — run lifecycle, streamed tokens, tool calls, state deltas — carried here over SSE. It says nothing about what the UI looks like. The frontend decides how to render each event; the protocol just guarantees what arrives and in what order.

Axis 2 · Payload

The abstraction spectrum

Everything a model emits toward a screen sits somewhere between two poles. At the constrained pole the model emits plain data and a trusted renderer owns every pixel. At the freeform pole the model writes the program itself. A2UI, Mermaid, Vega-Lite, AntV, and Metaphor3D are all points in the middle band: declarative languages a trusted renderer interprets.

The trade-off law of this axis: as expressive freedom grows, what you can deterministically validate shrinks — until validation is replaced by containment. Mermaid earns a four-layer repair ladder; freeform HTML gets a shape check and a locked sandbox (allow-scripts only, never allow-same-origin).

A2UI is not "between components and HTML" — it sits at the component end, and it differs in kind. The content DSLs describe things (a diagram, a chart, a scene); the renderer owns all interactivity. A2UI describes interfaces: a component tree plus actions wired back to the agent. In ArchiSlop the actions are pinned to two intent routes (archislop_fixSelected, archislop_fixAll), and the model never authors A2UI JSON directly — it writes critique markdown, and buildCritiqueActionableA2uiMessages builds the UI deterministically on the server. Same spectrum, different column: content language vs. UI language.
Axis 3 · Placement

MCP Apps: UI inside someone else's client

MCP Apps (SEP-1865) answer the placement question. An MCP server registers HTML bundles as ui://archislop/*.html resources; when a tool call carries _meta.ui.resourceUri, the MCP host — Claude Desktop, VS Code, Cursor — renders that HTML in a sandboxed iframe next to the conversation. The precision that matters: the UI is for the human using the LLM client. The model itself still sees the tool's JSON result; it never "looks at" the pixels.

All three at once

One critique run, every layer

The layers are complementary because a single feature crosses all of them. Follow one Critique click:

  1. transport  The web UI opens an AG-UI run: POST /api/copilotkit/agent-stream, operation analyze. Phases and tokens stream as STEP_* and TEXT_MESSAGE_* events.
  2. payload · data  The LLM writes plain markdown — content, not UI — including an ## Actionable section.
  3. payload · UI DSL  The server parses that markdown and deterministically builds A2UI messages, emitted as a CUSTOM name:"a2ui" event on the same wire.
  4. placement · web  CritiqueA2uiSurface.jsx renders the checklist with @a2ui/react. "Fix selected" fires a fixed action name that maps to the validated intent route — never an arbitrary model-chosen action.
  5. payload · content DSL  The fix run edits the Mermaid slot through the four-layer validation ladder, and the canvas re-renders from STATE_SNAPSHOT.
  6. placement · MCP host  Meanwhile a guest agent in Cursor calls open_critique_review; the critique-map MCP App shows the same bullets in its iframe, and a human can queue request_critique_fix — which arrives back in the web app over session-events.

One session state, three surfaces, one trust model: models author content; servers author UI; sandboxes contain code.
